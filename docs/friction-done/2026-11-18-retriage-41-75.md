# Re-triage of in-game tests 41–75 against the logs (2026-11-18)

Task: for each open in-game test 41–75, decide whether the development logs
could settle it, with evidence, and write docs/in-game-tests-retriage-41-75.md.
Branch: worktree-agent-a40c14ffc42e03e71 (base 1e1e7a8).

## 1. No query layer over the raw fixtures for "who did what when"

- **What happened:** nearly every test needed the same few views: a
  per-operator cast/hit timeline, a buff's listing spans (`since` to last
  listed hit), the hits around a cast, which weapon an operator wears. None
  exists as a command. I wrote about 15 throwaway scripts in scratch/
  (lib, idx, wpn, t41…t74), each re-deriving the same loops. `efsim zmdlogs
  hits --json` gives engine readings but not listing spans or neighbouring
  events. Roughly half the session went to this plumbing.
- **Cause:** the views in packages/logs/src/views.ts target engine
  diagnosis (differences, replay, stagger), not "does the log show case X".
  The template (scripts/scratch-template.ts) only loads the checked
  fixtures through the engine.
- **Suggestion:** add `efsim zmdlogs timeline <fixture> --operator <op>`
  (casts and hits in one list, relative to a chosen cast), `efsim zmdlogs
  spans <fixture> <buff-regex>` (each distinct `since`, last listed hit,
  source, value) and `efsim zmdlogs wearers <weapon-or-gear regex>` (log,
  operator, potential, skill levels). Export a `loadAllFixtures()` returning
  raw fixtures from verified, pending and multi-target without the engine.
- **Why it helps:** triage and diagnosis agents stop rewriting the same
  scripts; results become comparable between agents.

## 2. Operator IDs are not English names and there is no lookup

- **What happened:** the logs and kit files use internal IDs (`chr_0011_seraph`
  is Xaihi, `chr_0014_aurora` Snowshine, `chr_0028_wulfa` Rossi,
  `chr_0024_deepfin` Alesh, `chr_0009_azrila` Ember, `chr_0021_whiten`
  Estella, `chr_0022_bounda` Fluorite). I first took `aurora` for Xaihi and
  `karin` was unclear until I found a kit-batch file name; I had to infer
  names from team lists in `zmdlogs list`. Valiant's extra hit is even
  logged under another operator's event key (`chr_0015_lifeng_ultimate_skill`).
- **Cause:** `efsim find` looks up by name to ID but there is no table of
  all IDs in the docs, and `zmdlogs list` prints names, not IDs.
- **Suggestion:** `efsim find --operators` listing ID, English name; print
  IDs in `zmdlogs list` (or a `--ids` column); note in
  docs/design/data.md the weapon-skill hit keys logged under a wearer's
  or another operator's event name.
- **Why it helps:** removes a class of silent misreads.

## 3. Hits cache is slow to build by hand and shapes differ between sources

- **What happened:** to query engine readings across 79 logs I looped the
  CLI per fixture and trimmed 100+ MB of JSONL into the scratchpad. A first
  attempt with a heredoc was refused by the sandbox guard; a long node
  command was refused as "too complex", costing retries.
- **Cause:** `zmdlogs hits --json` prints one fixture, with a leading text
  line, to stdout; no all-fixtures mode.
- **Suggestion:** `zmdlogs hits --all --json --out <file>` (JSONL, no text
  header, optional field filter). Mention in CLAUDE.md that scratch scripts
  must be Write-tool files, which it does, but give a ready runner snippet.
- **Why it helps:** one command instead of a custom cacher.

## 4. Stale or missing facts about what is logged

- **What happened:** the triage said "No Perlica finisher" and "No log" for
  Avywenna; both exist. It also claimed "Link is never listed" etc.
  without counts. Facts such as "Valiant's hit key", "Wild Wanderer's
  listing starts at the combo" had to be rediscovered.
- **Cause:** the 2026-11-13 triage was a model pass, kept as a table with no
  generated check, and no index of which operator or weapon is in which log.
- **Suggestion:** generate a docs table (`operator/weapon/gear -> logs`)
  from the fixtures (a script plus `npm run check` staleness test, like the
  journal) and link it from in-game-tests-log-triage.md.
- **Why it helps:** "LOGS IF" vs "LOGS" would be a lookup, and cannot rot.

## 5. Cast events missing for several operators

- **What happened:** Avywenna, Arclight's battle skill, Endministrator and
  Alesh combos have no casts in some logs (`casts` empty), so cast timing
  had to be inferred from hit events (`combo_skill` hit groups). Easy to get
  wrong where hits come in multi-target groups of 11–44.
- **Cause:** documented in the triage ("Casts are logged for some operators
  only") but not in a machine-readable form.
- **Suggestion:** have `zmdlogs casts` print, per operator in a log, whether
  casts are logged and, if not, the inferred cast times it uses.
- **Why it helps:** one shared inference instead of per-script grouping.

## What worked well

- The cached `zmdlogs hits --json` (verdict, class, modifiers, zones) made
  engine-versus-log questions (Jade Vessel, Starry Beach, Link, Chen's P1)
  answerable in one filter.
- docs/design/data.md "What the log records" (cast lag, status keys) saved
  time; the Logs-first rule and in-game-tests.md headings made scope clear.
- `node scripts/setup-worktree.ts` and the CLI ran first time; fixtures are
  plain JSON, so ad hoc analysis is cheap.
