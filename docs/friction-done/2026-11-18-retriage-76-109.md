# Re-triage of in-game tests 76-109 against the logs (2026-11-18)

Task: for each open in-game test 76-109, decide whether the development logs
could settle it, with evidence and instance counts, written to
docs/in-game-tests-retriage-76-109.md. Branch: the worktree of
`claude/beautiful-rubin-rpg8vp`.

## 1. No one-call way to ask "what does the log say around this skill"

- **What happened:** nearly every test asked the same question: for operator X,
  around each cast of skill Y, which hits, effect lanes (with `since`),
  other operators' casts and reactions occur in a window? There is no
  command for it. I wrote about 12 throwaway scripts (`scratch/*.cjs`:
  purr, lifeng2, lh2/lh3, lr, lr2, lr3, zh, zh2, mifu, ra, ra2, ra3),
  each re-deriving the same loops over `fx.casts` and `fx.hits`. This was
  most of the time spent.
- **Cause:** `efsim zmdlogs casts|replay|stagger|differences|hits` answer
  engine-check questions (placement, replay, verdicts), not raw "timeline
  around an event" questions; the raw fixture shape is only learned by
  printing it.
- **Suggestion:** add `efsim zmdlogs window <fixture|--all> --operator <op>
  --skill <regex> [--before ms --after ms]` that prints, per matching cast,
  the window's hits (deduplicated per 250 ms), other operators' casts and
  the effect lanes that start or end inside it. Also `efsim zmdlogs lanes
  --buff <regex>` listing each lane (`since`, first and last hit, values,
  operators) per fixture.
- **Why it helps:** most re-triage questions (Link, Hypothermia, Long
  Heritage lanes, Zhuang combos) become one command; no hand-rolled
  scripts that each risk a different bug (I had a wrong event-name regex
  once).

## 2. Name lookups: operator ids, weapon ids and event names are opaque

- **What happened:** ids like `chr_0028_wulfa` (Rossi), `chr_0032_lizhiyan`
  (Arcane), `chr_0007_ikut` (Akekuri), `chr_0011_seraph` (Xaihi) can't be
  guessed; a grep for "rossi" returned nothing and I thought Rossi had no
  events. Weapon names needed a custom script over `loadGameData().weapons`.
  Event names (`combo_skill_abilityrange_1_1_potential_3`,
  `sword_triggerd`, `normal_skill_ult_abilityrange`) are unexplained.
- **Cause:** no name-to-id table in the docs or the CLI output for logs;
  `zmdlogs list` prints display names but not ids.
- **Suggestion:** `efsim zmdlogs list --ids` (team with ids and weapon
  names), and a short docs table (operator display name, id) in
  docs/design/data.md "What the log records"; ideally a command that
  lists the distinct event names per operator with counts and the kit
  skill each maps to.
- **Why it helps:** saves the "is it absent or misnamed" detour, which cost
  several wrong first conclusions.

## 3. The log's listing has undocumented blind spots

- **What happened:** whether a test is log-decidable depends on what is
  listed. I found by trial that the weapon team buff (Long Heritage's
  `teamspell`) appears on the wielder's hits only; Vulnerable lanes carry no
  stack counts; Haste, shields, heals, Whirlpools aren't listed. Each
  discovery changed a verdict.
- **Cause:** the "What the log records" section covers times, casts and
  status keys but not which buff kinds are listed on whom.
- **Suggestion:** add a "what is and isn't listed" paragraph to
  docs/design/data.md with those facts, and have the triage doc link it.
- **Why it helps:** a test's verdict (LOGS vs GAME ONLY) is mostly this
  question; one place to look.

## 4. `zmdlogs hits` takes a path, not an id, and mixes verdict and raw output

- **What happened:** `efsim zmdlogs hits 10df8c76ccda` failed (ENOENT); the
  fixture needs its full path under `fixtures/<dir>/zmdlogs-<id>.json`, while
  the triage and docs cite 4-character ids. The multi-target logs (10df)
  are not engine-checked, so the hits output there is all "mismatch", which
  I only noticed afterwards.
- **Cause:** commands accept paths only; ids are a doc convention.
- **Suggestion:** resolve an id or unique prefix (`10df`) to its file in
  every zmdlogs command, and print a one-line "multi-target: not checked"
  note.
- **Why it helps:** removes a lookup step and a misleading output.

## 5. Sandbox command-shape rules cost retries

- **What happened:** a heredoc/`cat >` plus a loop was refused as too
  complex; I had to switch to the Write tool for every script.
- **Cause:** documented in CLAUDE.md, but easy to forget when many small
  scripts are needed.
- **Suggestion:** ship a `scratch/` helper module (`scripts/scratch-fixtures.cjs`
  or a TS export) that loads every development fixture, so a script is
  only the question.
- **Why it helps:** fewer files per question; my `inv.cjs` did exactly this.

## What worked well

- CLAUDE.md's rules on hold-out logs and `listLogs`/`zmdlogs list` made the
  safe fixture set obvious; the fixtures are plain JSON, easy to script.
- `zmdlogs hits --json` with `landing.modifiers` showed directly whether the
  engine applied Rapid Ascent to a hit and the predicted value: the best
  single tool for the Stagger question.
- The triage doc's per-test lines and fixture ids gave a fast starting point.
