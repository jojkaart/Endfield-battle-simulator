## 1. The SP shortfall is visible only through a probe that replays every log again

- **What happened:** the question of the whole task was "how many logs, casts and SP does the replay's own SP run
  short by, under this code or that reading". No view or measure line says it: replayCast raises SP silently and
  BuffReplay.spTopUps is read by nothing but scripts. Each count was a scratch script replaying all 65 development
  logs in one process (scripts/probes/sp/shortfall.ts, readings.ts): 3–5 min alone, 10–40 min under the machine's
  load beside measures, five runs in all (the baseline, the fix, the start and pause variants twice). A measure of the
  same code already replays every log, and its result says nothing about SP.
- **Cause:** spTopUps isn't in the per-log record measure and snapshots:update write (scratch/measure/<run>/, the
  log-verdicts snapshots), so neither measure's summary nor `--variant` runs can report it; a replay fact a lead
  cares about needs its own pass.
- **Suggestion:** a describing snapshot key per log, `sp short` (the top-ups' casts and SP, rounded), and a summary
  line in measure ("Team SP the replay lacks: 15 logs, 27 casts, 706 SP → …", per row, hold-outs as aggregates);
  `zmdlogs replay` printing a TOPUP line per short cast (time, operator, skill, SP), so one log is one command.
  Then `measure --variant sp-regen=ticks --variant sp-start=full` answers in one queued run what took four probe runs.
- **Files:** packages/logs/src/buffreplay.ts (spTopUps, already there), scripts/measure.ts, scripts/accuracy.ts
  (isDescribingKey), packages/logs/src/views.ts (the replay view's lines), tests/snapshots/.
- **Why it helps:** the SP model moves every simulated team number; a change that makes the replay's casts less or
  more affordable would show in every measure instead of only when someone thinks to probe. Cost: one key per log.

## 2. The replay view's EVENT line names the wrong made cast

- **What happened:** in `efsim zmdlogs replay 04d4`, "264.25 EVENT Purrchena normal_skill …: the replay made it at
  260.67" and "275.51 EVENT …: the replay made it at 269.80": each event pointed at the cast made for the event before
  it, which read as the replay shifting casts by 3–6 s. Sorting out which cast the replay made for which event took
  the casts listing, the fixture's casts and the FORCED lines side by side.
- **Cause:** views.ts replayFate's `ofEvent` takes the first made cast of the skill whose start lies between the
  event less the skill's whole duration (6.13 s for her battle skill) and the event plus 100 ms, not the nearest one.
- **Suggestion:** pick the made cast whose start is nearest the event within that span (or the one the cast assembly
  made from this very event, BuffReplay.made's cast with `start` equal to the event's), and say "none" otherwise.
- **Files:** packages/logs/src/views.ts (replayFate, ofEvent), tests/views.test.ts.
- **Why it helps:** the EVENT line is how one reads what the replay did with each press; a wrong pairing sends a
  diagnosis after a lag that isn't there. No verdict moves.

## 3. No record of where the replay's SP came from

- **What happened:** to see what the replay granted in 79cc's opening (why four battle skills in 11 s ran 92 SP
  short) I sampled `stateAt` frame by frame and printed every SP change beyond 8/s (scripts/probes/sp/grants.ts),
  then guessed the source of each from the casts around it (a +20.3 at 12.57 s took three looks to place: Laevatain's
  empowered hit, already granted, which I had first taken for a missing P1 return and patched in the kit and the
  engine before seeing it was there).
- **Cause:** TimelineState keeps energyGained per operator and source, but nothing for SP: gainSp records only the
  overflow and the returned share.
- **Suggestion:** an `spGained` statistic like energyGained (per operator and source: a hit's skill and hit id, a
  trigger, regeneration, a dodge), and a `zmdlogs replay --sp` (or the grants probe as a view) listing each grant and
  spend with its source. search.ts's state key leaves it out as a statistic.
- **Files:** packages/engine/src/timeline/resources.ts (gainSp), timeline/state.ts, planning/search.ts (STATE_KEY),
  packages/logs/src/views.ts.
- **Why it helps:** "which SP did the replay give, from what" is the first question of every SP lead (Akekuri's
  flares at the cap, test 112, asks it too); a record answers it without a frame scan or a wrong patch.

## 4. scripts/edit.ts wants whole lines; one long import line can't be edited with it

- **What happened:** adding `engineReading` to search.ts's one-line import of 40 names, the edits file's old text
  had to be the whole 600-character line, so I fell back to `sed -i '13s/…/…/'`; an edits block with a partial line
  failed with "the block isn't closed" after I trimmed the file by line count. Twice an edit to docs/in-game-tests.md
  matched four times (the "Not testable by hand" line repeats) and needed the heading above it.
- **Cause:** edit.ts matches whole lines by design (safe), and long import lines are the repository's style.
- **Suggestion:** an `<<<<<<< in-line` block kind that replaces a substring inside exactly one line (the line found
  by the substring, which must occur once in the file), for imports and long table rows.
- **Files:** scripts/edit.ts, tests/edit-guard.test.ts.
- **Why it helps:** an import edit is the most common small change; today it means a sed, which the guard allows
  only without backticks. Low risk: the substring must be unique.
