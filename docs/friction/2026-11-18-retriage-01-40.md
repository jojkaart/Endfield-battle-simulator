# Re-triage of in-game tests 1-40 against the logs (2026-11-18)

Task: re-read every open in-game test from 1 to 40 and say whether the
development logs could decide it (docs/in-game-tests-retriage-01-40.md).

## 1. No ready query tool over the raw fixtures

- **What happened:** nearly every question ("how many of Si's battle skills
  are followed by her Final Strike within 0.7 s", "which logs list this buff,
  from which source, from when to when") needed a new script. I wrote about
  30 small scripts in scratch/ (timeline per log, buff intervals by
  `source`/`since`, event census, cast-to-hit gaps). Each re-implemented
  loading the fixture directories (verified, pending, multi-target, never
  holdout), clustering hits, and grouping effects.
- **Cause:** `efsim zmdlogs` has views for the engine's disagreements
  (`check`, `differences`, `casts`, `replay`, `stagger`) but none for the log
  itself; the scratch template only shows the engine path.
- **Suggestion:** an `efsim zmdlogs query` family on the raw fixtures:
  `census events|buffs [regex]` (which logs, how many hits), `timeline
  <fixture> [--op --event --buff]` (casts, hits, poise, listed buff
  intervals), `windows <buff-regex>` (since, first and last listed hit, next
  unlisted hit, per source), and `after <cast-regex> <hit-regex> --within ms`
  (gap histogram). Export the loader (non-holdout fixture list) from
  packages/logs so scratch scripts import it.
- **Why it helps:** most triage and diagnosis questions become one command;
  the holdout exclusion lives in one place instead of every script.

## 2. Checking one log through the CLI is slow and chatty; all logs is a trap

- **What happened:** `efsim zmdlogs hits` with no fixture silently runs every
  log and hit the 120 s tool timeout; with one fixture it still takes tens of
  seconds and emits 2 MB of JSON. Under `scripts/with-lock.ts` the lock
  notice goes to stdout, so my `--json > file` output began with a
  non-JSON line and the parser failed.
- **Cause:** `hits` defaults to all logs; with-lock prints its heartbeat on
  stdout; no cached verdicts to read.
- **Suggestion:** require a fixture (or `--all`) for `hits`; with-lock
  messages to stderr; let `snapshots:update` also write a compact verdict
  dump (per hit: log, t, operator, event, class, predicted) that scratch
  scripts can read, like the dump I had to build with `checkLog`.
- **Why it helps:** verdict questions (which hits match plain, per event)
  take seconds without CPU or the shared lock.

## 3. The stale or ambiguous parts of the log format cost interpretation time

- **What happened:** several answers depend on what a field means and the
  docs only partly say: `LogEffect.since` (first application or latest
  refresh?), a cast event's time against the press (battle skills "at the
  placed start", ultimates lag 1.9 s), Liino's `normal_skill` cast also
  logging End Stance and the stance's repeats, Gilberta's battle skill having
  no cast event but a five-hit field. I rediscovered each from the data and
  the batch kit docs. Test texts also carry stale premises (test 6 still
  cites the v58 log and a "2x" the kit already explains).
- **Cause:** facts live in data.md, kit-batches and open-problems separately;
  in-game-tests.md is not updated when a kit explains its question.
- **Suggestion:** a "log fields by operator" table in data.md (which skills
  log a cast, which only hits, what an event name covers); when a kit batch
  closes a question, strike or link the test in in-game-tests.md in the same
  change.
- **Why it helps:** fewer wrong first readings; stale tests stop looking
  open.

## 4. Sandbox command rules cost retries

- **What happened:** heredocs, pipes mixed with `git`, and `sleep` were
  refused, and one `cd ... && node` chain was refused as too complex; each
  needed a rewrite into a Write-tool file plus a plain command.
- **Cause:** the guard judges text, not intent (already documented in
  CLAUDE.md).
- **Suggestion:** a scratch-template variant that takes the fixture prefix
  and a regex from argv, so one-off questions need no new file.
- **Why it helps:** fewer round trips.
